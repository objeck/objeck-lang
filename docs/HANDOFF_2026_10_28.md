## Nightly Hardening

Run 40672224592 tested master at 3283567435, i.e. after #1434 and #1436. It
finished with failures. A partial triage was done before the reboot; its
findings are below.

**Fixed.** Every fuzz, verify-minor, verify-major and stress step passed on all
five legs. So there are NO heap-verifier or GC failures left: #1436 cleared all
the B3 hits, and #1434 cleared the harness failures. linux-x64 and linux-arm64
passed every step.

**Still failing.** Four tests, all in the differential step:
- **windows-x64 and windows-arm64, query_url_cache_processes, s3/jit1 only:**
  "every query of 1440 in 60 processes read one whole, current version (447 /
  97 did not)". It needs a closer look.
  - A local repro (CI win-x64 binaries, s3 with `--jit=1`) got 2 of 1440
    wrong. Both were "no response from the server (after 21 s)", and none were
    stale or partial.
  - The question: were the CI failures also "no response"? CI logs keep only
    the first differing line, so rerun locally several times, in each config.
  - If they were "no response", it is the Windows loopback server under load
    (the #669 family). Track it after the release.
  - If any were stale or partial, it is a real Windows URL-cache defect and
    should BLOCK the release.
- **windows-x64, query_server_concurrent, s3/default:** 1 of 432 answers
  wrong. Likely flaky; track it after the release unless it recurs.
- **windows-x64, server_bind_address, s0/off and s3/off:** an accepted peer
  address read back as 'Nil'. Likely a Windows socket flake; track it after the
  release.
- **macos-arm64, query_index_concurrent:** timed out at 180 s at s0/off and
  s3/off. It persists from the last run, interpreted configs only. The test is
  probably too slow interpreted: raise the timeout, shrink the test, or profile
  it. Track it after the release.
