# Handoff: Windows loopback connect stalls (#1443, #1461), 2026-10-31

For the Kompute session. It picks up the diagnosis of #1443 from the laptop session
that ran it (the "net/AI" session of the 10.2 stabilization). 10.2 ships with #1443
as a documented known issue; a fix found here is its own PR against master, at the
coordinator's call for 10.2 or 10.3.

Read first: issue #1443 and its comments (issuecomment-6540789827, -6543477441), #1461.

## The symptom

`query_url_cache_processes` (60 child obr processes, about 1,440 HTTP requests a run
against an in-process `Web.HTTP.Server.WebServer` on loopback) occasionally has 1 to 3
queries fail with `no response from the server (after 21.0 s)`. Locally, 6 of 60 runs
of CI's own harness (`programs/regression/run_differential.py`) failed. On CI the
nightly `s3/jit1` configuration fails far harder (97 to 447 bad queries in a run).
That difference is NOT explained yet.

## What is now established

1. **The 21 s is a connect that never completes.** `CONNECT_FAIL d=10060`: Windows'
   SYN retries run out. A new child was given an ephemeral port that, from the
   server's point of view, still belongs to an open connection, so its SYN is dropped.
   (Windows keeps no TIME_WAIT on loopback, so a port is reusable at once.)
2. **That old connection was closed by its client, but the server never heard.**
   Traced from both ends (patch below), all three failures of one run, e.g. port 62682:
   - 08:27:32.026 client CONNECT, server ACCEPT
   - 08:27:32.222 client CLOSE: `shutdown(SD_SEND)` and `closesocket` both succeed
   - nothing reaches the server: its read times out at 08:28:02.078 (`READ_ERR 10060`,
     the 30 s receive timeout) and only then does it close
   - at about 08:27:46 another child gets port 62682 and its connect stalls 21 s
   The closes are mid-process, not at process exit, and nothing was left unread at
   close (`FIONREAD` logged 0 on every close).
3. **The rate.** In one traced run of 9,818 connections the server's read ended: EOF
   6,394 (median 89 ms after the client's close), reset `10054` 3,294 (median 4 ms
   after), never (30 s timeout `10060`) 53. So about a third of clean client closes
   arrive at the server as a reset, and about 0.5% arrive as nothing at all.
4. **It is Windows, not Objeck.** `rstprobe.py` does the same exchange in plain
   Python sockets (thread-per-connection server with a 30 s receive timeout and
   TCP_NODELAY, reply as two sends; client reads the whole reply, `shutdown(SHUT_WR)`,
   `close`). With 6 client threads and 3,000 connections, on a laptop that was also
   running the soak: `{'eof': 1971, 'err10054': 766, 'err10060': 14}`, and a client
   connect failed with WinError 10060. Same three outcomes, same rough shares. The
   same stall was also seen once between two `asus_framework.exe` processes.
5. **Ruled out earlier:** port exhaustion; cache file locking; HttpClient leaving
   sockets open (every path closes); Windows not notifying a peer on close or exit in
   isolation (it does, immediately, when the machine is quiet).

6. **Waiting for the server before closing makes it worse.** `rstprobe.py`, 3,000
   connections, 6 client threads, laptop under the soak's load:

   | client close | server EOF | reset 10054 | nothing, 30 s 10060 |
   | --- | --- | --- | --- |
   | `shutclose` (Objeck today) | 1,971 | 766 | 14 |
   | `close` | 2,015 | 781 | 11 |
   | `drain` (shutdown, read to EOF, close) | 770 | 231 | 237 |

   In `drain` the client socket stays open after its FIN, so nothing on the client
   side can have cut the close short, yet the server's stack never received the FIN
   in 237 cases (several client threads also died on 21 s connect timeouts, hence
   the smaller total). The netstat watcher agrees: the server end stays ESTABLISHED,
   not CLOSE_WAIT. So the earlier theory, a reset that is lost, does not explain
   it: the FIN itself goes missing, and a client-side close sequence is unlikely to
   be the fix.

Open question: why a FIN on loopback is not delivered (or not retransmitted) under
load. Things to try on Kompute: whether it happens on an idle machine at all; whether
it depends on the number of threads blocked in `recv` on the server (thread per
connection) versus one thread using `select`/IOCP; whether Windows Defender or
another filter driver on the loopback path is involved (the `asus_framework.exe`
case suggests a system-wide cause, so compare with filters disabled if allowed);
and a packet capture (`pktmon`, needs an elevated prompt, which the laptop session
did not have) to see whether the FIN is ever sent.

## Next steps

1. **Repeat the Python probe on Kompute,** idle and then under load (run the soak
   beside it). If an idle 16-core box shows no resets, load is a condition; record it.
2. **Find what loses the FIN** (the open question above). `rstprobe.py` takes a mode
   (`shutclose`, `close`, `drain`) and can be changed to vary the server (thread per
   connection versus `select`) and the load. A packet capture settles whether the FIN
   is sent at all.
3. **Fix where the cause is.** If no close sequence can be made reliable, the
   defense that does not hide anything is on the server: a stale server end is what
   blocks the reused port, for as long as the 30 s idle receive timeout. Treat that
   as a design question for the coordinator, not a quiet timeout change.
4. **Prove it old vs new:** the soak with the tracing VM, before and after, enough
   runs that 6/60 versus 0/N means something (60 runs each at least), plus the
   Python probe. Then the full regression suite both passes and the network tests.
5. **Explain CI's s3/jit1 rate.** The nightly artifact holds only a summary. Making
   `run_differential.py` keep per-config output for failures would let CI tell us
   whether its failures are all 21 s connects. That can be its own small PR.

Rules that apply: fix the cause, no retries or longer timeouts to hide it; one PR
per fix; merge only when every CI leg is green; never commit TESTS.md; no @-mentions
of session names in GitHub text.

## Tools (in `docs/handoff_net_1443/`)

| File | What it is |
| --- | --- |
| `sock_trace.patch` | Temporary VM tracing, never to be merged. With `OBJECK_SOCK_TRACE=<folder>` every obr process writes `sock_<pid>.log`: `CONNECT`, `CONNECT_FAIL`, `ACCEPT`, `READ_EOF`, `READ_ERR`, `UNREAD:<bytes>` and `CLOSE`, each with a wall-clock time in microseconds since 1601, pid, thread, handle, local and peer port and a detail code (WSA error, or byte count). `git apply`, build `core/vm/vs/vm.vcxproj` Release x64, copy `core/vm/Release/win64/obr.exe` into a scratch `bin` beside a `lib` junction to `deploy-x64/lib`, then `git checkout -- core/vm`. |
| `instrument.py`, `instrument2.py` | The scripts that produced the patch (in that order), if it stops applying. |
| `soak2.ps1` | Runs `run_differential.py` on the test N times with a given bin, one trace folder per iteration, kept only when the iteration fails. `-Bin <scratch>\bin -Times 30 -Out <folder>`. |
| `pair.py` | Pairs each client connection with its server end from a trace folder and prints how the server's reads ended. |
| `synwatch2.py` | Polls `netstat -ano` every 100 ms; logs any SYN_SENT older than 2 s with the history of its port pair and the owning processes. `python synwatch2.py out.log <seconds>`. |
| `rstprobe.py` | The pure-Python reproduction: `python rstprobe.py <shutclose|close|drain> <connections> <threads>`. |

Kompute has never run these: build and verify first (both regression passes), and
run `hostname` so results are attributed to the right machine.
