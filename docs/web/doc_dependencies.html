Third-party dependencies: where each platform gets them, and how to check versions

All documentationView docs/third_party_dependencies.md on GitHub

Objeck pins little itself. The HTTP/2 and HTTP/3 stack (nghttp2, ngtcp2, nghttp3, AWS-LC) is built from pinned sources by tools/deps/build_quic_deps.sh and linked statically on Linux and macOS. The TLS, audio, vision and inference libraries come from each platform's package channel at build time, so security fixes arrive with that channel — and a channel that is behind is behind for every release built on it. This page records the provenance so an audit is a lookup, not an archaeology dig. The few versions the tree pins are in tools/deps/build_quic_deps.sh (AWS-LC), tools/deps/build_macos_deps.sh (the macOS static builds) and the $opencvVersion of the Windows OpenCV download in the three build workflows.

mbedTLS and threads

mbedTLS protects the state its connections share (the PSA key store that TLS 1.3 uses, a server's private key and random generator) only when it is built with MBEDTLS_THREADING_C. The Debian and Ubuntu packages and the macOS build (core/lib/openssl/macos/mbedtls_config.h) are; vcpkg's default mbedtls port, which the Windows builds link, is not (its pthreads feature turns it on, at the price of shipping pthreads4w). Objeck runs TLS connections on many threads, so the VM checks the macro it was compiled against: without it, every call into mbedTLS is made holding one process-wide lock (TlsLibraryLock in core/vm/common.h), let go while a call waits on the network. That is correct with either kind of library, and on Windows it means the cryptography of concurrent TLS connections runs one at a time. Linking a Windows mbedTLS built with threading (MBEDTLS_THREADING_ALT over SRW locks needs no extra DLL) would lift that with no change to the VM beyond registering the lock functions; programs/regression/tls_concurrent_connections.obs is the test either way.

Checking what a build actually used

  • Windows: in the CI log's "Install Windows dependencies" step, vcpkg install names each port with its version (mbedtls:x64-windows@<version>). OpenCV x64's version is $opencvVersion in the workflows (and the 4120 in its DLL name); ONNX Runtime x64's is the NuGet version in core/lib/onnx/vs/packages.config. The vendored DLLs, SDL2 and the ARM64 QNN ONNX Runtime (1.23.0), carry theirs in their file-version resources ((Get-Item SDL2.dll).VersionInfo).
  • Linux: dpkg -l libmbedtls-dev libsdl2-dev libopencv-dev libmp3lame-dev on the runner image (ubuntu-24.04 — the image, not the tree, decides the version). The HTTP/2 and HTTP/3 versions are pinned in tools/deps/build_quic_deps.sh and recorded in its prefix's .quic-deps-stamp.
  • macOS: every third-party library is pinned in tools/deps/build_macos_deps.sh (version and sha256) and recorded in its prefix's macos-bundle/.macos-deps-stamp; HTTP/2 and HTTP/3 as on Linux (.quic-deps-stamp). The licenses ship under each library's licenses/.
  • Shipped tree: ldd lib/native/libobjk_crypto.so / otool -L / dumpbin /dependents names the exact runtime libraries a native module links, which is also what verify_native_libs.sh|.ps1 checks resolve.

What "audit" means here

  1. For the two libraries with a security surface exposed to the network — mbedTLS and nghttp2 (plus ngtcp2/AWS-LC on POSIX) — compare the version the runner image installs, or the version pinned in the table above, against upstream's supported branches (mbedTLS 3.6 LTS at the time of writing; 4.x is not API-compatible and is a migration, not a bump).
  2. For the Windows pins, OpenCV x64 ($opencvVersion and the cache keys in the three workflows, and the 4120 in the DLL and import-library names) and ONNX Runtime x64 (the NuGet version in core/lib/onnx/vs/packages.config, repeated in vs/vs.vcxproj and deploy_windows.cmd), compare the pinned version against the latest patch release and bump it everywhere it is named. The vendored SDL2 DLLs and ARM64 QNN runtime are bumped by replacing the files; ARM64 OpenCV follows vcpkg.
  3. Anything vendored (zlib) is our responsibility to update by hand.

A scheduled job that prints these versions into the CI summary would turn step 1 into a glance; it is not built yet.
