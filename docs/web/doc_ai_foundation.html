AI Foundation — Design (BERT is the first consumer)

← All docsdocs/AI_FOUNDATION_DESIGN.md on GitHub

Objeck is meant to be a language for AI research. Today it can run models (API.Onnx), call hosted models (API.OpenAI, API.Google, API.Ollama), and train small networks (System.ML). It cannot train or fine-tune a transformer, and every model needs hand downloading and, often, Python.

This document designs a foundation that closes that gap: tensors on CPU and GPU, autograd, nn modules, optimizers, data loading, safetensors and a Hugging Face hub cache, tokenizers, task pipelines, and ONNX as both a runtime and an export target. BERT, "like with Python's transformers", is the first thing built on it.

This is a design only. No library code changes with it. Target: the release after v2026.10.2.

Every number below marked measured was measured for this document on 2026-10-29 (method in the appendix). Everything else is labelled as an estimate or as something a phase must check.

Summary

  • Two tracks that meet.
    • Phase A, use models: download ONNX exports and tokenizers from the Hugging Face Hub, then run Python pipeline()-style tasks over the existing API.Onnx. It needs no new native dependency, and it ships value first.
    • Phase B, the training foundation: a binding of libtorch, PyTorch's C++ library and the same engine PyTorch runs on. Transformer architectures are written in Objeck over tensors and autograd, and load Hugging Face safetensors directly, as Rust's candle does. The end state needs no Python at all.
  • No deprecated or unmaintained dependency, not even as a fallback.
    • Rejected: ONNX Runtime's training API, deprecated in 1.20.0, which is why the earlier design, PR #1449, is superseded.
    • Rejected: TorchScript, which PyTorch's own source marks deprecated, and torch-directml, whose last release was in 2024.
    • Each dependency has a status table with primary-source evidence (§3).
    • Where the rule leaves a gap, the gap is stated: GPU training on Windows arm64, and on AMD GPUs under Windows (§3.3).
  • Existing programs keep compiling.
    • System.ML, API.Onnx, System.NLP and System.NLP.Onnx stay as they are.
    • New layers are new libraries. Old classes are kept, or gain a second backend behind the same API, and are never removed (§2).
  • The first end-to-end target is the user's lab model: DistilBERT fine-tuned as a malware classifier on Colab, run from Objeck through the Phase A TextClassifier. Later, the same model is fine-tuned in Objeck itself through Phase B.
  • First PR: TextClassifier over a local model folder, with a tiny checked-in DistilBERT-shaped fixture and a parity test (§11). It is small and testable, and it serves the lab directly.

1. Goals, rules and non-goals

Goals

  1. Use pretrained models by name, as in Python's pipeline("text-classification", model=...): no hand downloads, no Python.
  2. Fine-tune and train transformers in Objeck, on CPU and GPU, with the results matching PyTorch.
  3. One set of layers for all future AI work. Decoder LLMs, vision, audio, embeddings and RAG, and reinforcement learning all build on the same tensor, nn and hub layers, not on one-off wrappers.
  4. Parity is the test oracle. Every task and every training step is checked against PyTorch, transformers or tokenizers on fixed inputs, with stated tolerances.

Rules

  • No deprecated or unmaintained library, as primary dependency, fallback or optional path. Every dependency's status is cited from primary sources (§3).
  • Python-free end state. Python is allowed only in test-fixture generators that a developer runs to refresh fixtures, never on a user's path.
  • The project's own conventions:
    • a phased PR for each step;
    • objk_apis.json regenerated when library classes are added;
    • all libraries rebuilt after any compiler change;
    • TESTS.md never committed in a PR.

Non-goals

  • Writing tensor kernels or an autodiff engine in Objeck. That was ruled out before #1449, and it stays ruled out. libtorch supplies both.
  • Distributed or multi-node training, and serving at scale.
  • Replacing hosted-model clients (OpenAI, Gemini, Ollama). They stay, and agents keep using them (§4).

3.2 Rejected

  • ONNX Runtime training API.
    • Evidence: the v1.20.0 release notes say "All ONNX Runtime Training packages have been deprecated. ORT 1.19.2 was the last release…".
    • Consequence: PR #1449, which used it, is superseded by this document.
  • TorchScript / torch.jit.
    • Evidence: PyTorch's own docstrings in torch/jit/__init__.py, torch/jit/_freeze.py, torch/jit/_fuser.py and torch/jit/_async.py read "TorchScript is deprecated, please use torch.compile instead". torch/csrc/jit/frontend/script_type_parser.cpp adds "2024.08.14: Since we are starting to deprecate Torchscript usages".
    • Consequence: no TorchScript models and no torch::jit::load. Architectures are defined in Objeck instead (§7).
  • torch-directml.
    • Evidence: its last PyPI release is 0.2.5.dev240914, on 2024-09-15. Its last GitHub pre-release is 2024-08-19. The microsoft/DirectML README opens with "DirectML is in maintenance mode" and points to Windows ML.
  • Python-side export tools on the user's path (optimum, torch.onnx.export).
    • They are maintained.
    • Why rejected: they break the Python-free rule. Phase A downloads exports that already exist; Phase E writes ONNX from Objeck.
    • They stay acceptable for the lab's own Colab notebook, which is already Python (§9).

6. Language and VM fit

6.1 One Tensor class, dtype as a value

The compute tensor is System.AI.Tensor.Tensor: a handle to a libtorch tensor, plus a reference to any Objeck array it views.

  • Dtype and device are values on the tensor, not type parameters. Code like x->To(DType->F16)->To(Device->Cuda(0)) changes them at run time. A generic Tensor<T> would put the dtype into the static type and break that. PyTorch, candle and JAX all keep the dtype dynamic for the same reason.
  • Generics still serve the layers above:
    • Module holds Vector<Parameter>;
    • DataLoader<T> yields a user's batch type;
    • Map<String, Tensor> is the safetensors state dict.
  • API.Models.Tensor stays the interchange type for named model I/O. The core tensor converts to and from it:
t := Tensor->From(api_tensor);
api := t->ToModelTensor("logits");

6.2 No operator overloading: methods, chained

Objeck has no operator overloading (docs/ROSETTA_HARDENING.md: "Objeck has no operator overloading. Arithmetic types expose named methods."). The tensor API is therefore method-based and fluent:

scores := q->MatMul(k->Transpose(-2, -1))->Mul(scale)->Add(mask);   # Python: q @ k.transpose(-2, -1) * scale + mask
probs := scores->Softmax(-1);
  • This is enough to write every architecture in §8.
  • Operator overloading is a language change, so it is decision L1: a + b, a * b and a @ b dispatching to Add, Mul and MatMul on any class that declares them. Recommended later, as its own design, once the tensor API exists and real model code shows where the method chains hurt. It is not a prerequisite for anything here.

6.3 Memory: native tensors, the GC, and zero-copy

  • Tensor storage is native memory owned by libtorch. An Objeck Tensor object holds the handle as an Int and stores no object references inside C++, so no WriteBarrier is needed. Results that come back as Objeck arrays are allocated by the VM in the old generation (docs/native_interface.md, and the native-allocation rule since PR #650).
  • Zero-copy from Objeck arrays is possible, but only for 64-bit types.
    • Objeck's Float is a 64-bit double and Int is 64-bit. Tensor->View(values : Float[], shape) wraps the array's memory as an f64 tensor (torch::from_blob). Int[] becomes i64, which is exactly what token ids need.
    • This is safe because arrays are born in the old generation, and "old objects are never moved" (docs/native_interface.md). The Objeck Tensor keeps a reference to the array, so the array lives as long as the view.
  • f32, the dtype models train in, needs one conversion at the boundary. Tensor->FromFloats(values, shape, DType->F32) copies and narrows. ToFloats() widens back. Inside a model, nothing crosses the boundary: activations and weights stay native from load to result.
  • Lifetime: no finalizers today.
    • Objeck has no AutoCloseable and no finalizers (docs/INFERENCE_ENGINES_PLAN.md §"Lifetime" asked the same question for ONNX sessions).
    • A forward pass creates hundreds of temporary tensors, so manual Close() per tensor is not workable. The design uses scopes: every tensor created inside a scope is freed when the scope ends, except the ones returned or marked to keep.
loss := Tensor->Scope(\() => {
  logits := model->Forward(batch);
  return logits->CrossEntropy(batch->GetLabels());     # survives the scope
});
  • Owned outside scopes: parameters (by their Module), optimizer state (by the optimizer), and tensors explicitly kept.
  • Native-side backstop: a debug counter of live handles, which the tests assert returns to the baseline after each step.
  • Finalizers, or a using-style block, are decision L2: a VM change, recommended as a separate design that would let scopes become a convenience rather than a requirement.

6.4 Autograd lives in libtorch; closures serve the training loop

  • Gradients are recorded and computed by libtorch's autograd, the same engine as PyTorch:
    • loss->Backward(), Tensor->NoGrad(\() => ...) and param->RequiresGrad(false) map directly onto it;
    • Objeck closures never implement a backward pass for built-in ops.
  • Where closures are used:
    • the bodies of Scope and NoGrad;
    • Trainer callbacks (on step, on epoch, on evaluate);
    • data-loader transforms;
    • later, custom autograd functions (a forward and a backward written in Objeck, through libtorch's custom Function).

The FEATURES guide's lambda forms (\() => body, and the annotated \(T) ~ R : (x) => body) are enough for all of these.

6.5 The JIT and native-call overhead

  • Every tensor op is one native call. A BERT-base forward is about 12 layers × ~25 ops ≈ 300 calls per batch, against about 1.5 s of compute for a batch of 32 at length 128 (measured, §10.2). Call overhead is noise at that scale.
  • Where it matters: RL with tiny networks and many small steps. B0 measures the per-call cost under the JIT and under the interpreter. If it is significant, the shim adds fused calls for the hot paths (Linear, attention) rather than changing the VM.
  • Threads: libtorch's intra-op pool does the parallel work. Objeck threads may each run their own models. A tensor shared across Objeck threads is the user's responsibility, as in PyTorch.

7.3 Hub client and cache (System.AI.Hub, ai_hub.obl)

What the Hub answers (measured with raw HEAD requests, no redirects followed):

  • GET https://huggingface.co/{repo}/resolve/{revision}/{path}
    • Small (git) files: 307 with a relative Location: /api/resolve-cache/models/{repo}/{commit}/{path}?….
    • Large (LFS/Xet) files: 302 to an absolute, signed CDN URL (https://us.aws.cdn.hf.co/xet-bridge-us/…&Expires=…&Signature=…).
  • The first response carries the metadata:
    • X-Repo-Commit, the commit the revision resolved to;
    • X-Linked-Size;
    • X-Linked-Etag, which is the file's SHA-256 for LFS files (it matches the lfs.sha256 that the API lists) and the git blob SHA-1 for small files.
  • The CDN answers Accept-Ranges: bytes, so interrupted downloads can resume.

What Objeck's HTTPS client does with that today (core/compiler/lib_src/net_secure.obs, net_common.obs):

  • Redirects work. It follows 301/302/303/307/308, and BuildRedirectUrl resolves a relative Location against the current host with https://.
  • Large files fail.
    • The whole body is read into memory, and WebCommon->ReadLength returns Nil above 256 MB (if(length > 256*1048576)).
    • Every fp32 base model fails: bert-base 438 MB, RoBERTa 499 MB, XLM-R 1,114 MB.
  • Tokens would leak.
    • @request_headers are re-sent on every hop, including a redirect to another host.
    • An Authorization: Bearer token for a gated repo would be sent to the CDN.
    • This is a security bug to fix before any token support ships. Strip Authorization (and cookies) on a cross-origin redirect, as curl and browsers do.
  • Checksums need streaming. Cipher.Hash->SHA256 takes one Byte[], so a 1.1 GB file would have to sit in memory to be hashed.

Required changes, all in Phase A2:

  • HttpsClient->GetToFile(url, path, headers) streams to a temporary file in chunks, follows redirects, and resumes with Range: bytes=N- when the server accepts ranges. It also gets HttpClient and HTTP/2 counterparts. No size cap: the cap exists to protect memory, and streaming removes the reason.
  • The cross-origin Authorization strip, with a regression test against a local server that redirects to a second port.
  • An incremental hash: Cipher.Hash->Sha256Init/Update/Final, or a Hasher object, over the native library behind Cipher.Hash. Git-blob SHA-1 for small files uses the existing SHA1 on "blob {size}\0" + content.

Design. TokenizerJson->Load(path) builds a pipeline object from the four stages. Each stage is a small class behind an interface, so new component types are added without touching the others:

  • Normalizers:
    • BertNormalizer (the existing WordPiece text cleaning, moved behind the interface);
    • Lowercase, Strip, Replace, NFC/NFKC, Sequence;
    • Precompiled: SentencePiece's normalisation table, a base64 blob of 316,720 characters in both the DeBERTa and XLM-R files. It holds a double-array trie and its replacement strings. Objeck parses the blob itself, about 200 lines. Its parity is tested on a full sweep of the Unicode planes, not only on sample text.
  • Pre-tokenizers:
    • BertPreTokenizer, WhitespaceSplit, Metaspace, Sequence;
    • ByteLevel: the GPT-2 split pattern, letters \p{L}+, numbers \p{N}+, contractions, and space handling. It is written as a hand-coded scanner, not as a regex, so it does not depend on the regex library's \p{…} support. WordPieceUnicode already has generated punctuation, control, mark and case tables. A4 adds letter (L*) and number (N*) category tables generated the same way. The bytes→unicode map is GPT-2's fixed table.
  • Models:
    • WordPiece (the existing algorithm);
    • BPE: merge ranks, a per-word cache, and continuing_subword_prefix and byte_fallback handling;
    • Unigram: Viterbi over the lattice of vocabulary pieces with their log-probabilities, and the unk score and fuse_unk.
  • Post-processors: TemplateProcessing (single and pair templates, special-token ids), RobertaProcessing, BertProcessing.
  • Decoders: WordPiece, ByteLevel and Metaspace. Fill-mask needs them to print the token.

TokenEncoding gains offsets (character start and end per token), word ids, sequence ids (0, 1, or none for specials), and overflow windows. NER and QA need the offsets to return character spans. New fields and methods are additive.

7.5 Task pipelines (System.NLP.Onnx, nlp_onnx.obl)

Shared base. TransformerTask handles everything every task needs:

  • it opens a model folder (a local path or a hub snapshot): config.json, the tokenizer and the ONNX file;
  • it reads the session's inputs and outputs, sending only declared inputs, as §7.2 requires;

How each task reads the model, matching transformers behaviour:

  • Text classification.
    • Labels come from config.json id2label; LABEL_n when absent.
    • The score uses softmax, or sigmoid when problem_type is multi_label_classification or there is a single label, which is what transformers' function_to_apply does by default.
    • top_k returns all labels sorted.
  • Token classification.
    • Per-token softmax over logits [batch, sequence, labels].
    • The aggregation strategies are NONE, SIMPLE, FIRST, AVERAGE and MAX, with the same sub-word and B-/I- merging rules as transformers' TokenClassificationPipeline.
    • Character spans come from the offsets.
    • The default is NONE, as in Python.
  • Question answering.
    • Pairs are encoded question-first with only_second truncation, and p_mask excludes the question and the specials.
    • Answers are spans with start ≤ end and length ≤ max_answer_len (15).
    • The score is the product of the start and end probabilities.
    • handle_impossible_answer is supported for SQuAD 2 models.
  • Fill-mask.
    • Softmax over the vocabulary at each mask position, top_k (5), and the decoder for the token text.
    • The output is [batch, sequence, vocabulary], so about 15.6 MB of floats per text at length 128 for BERT. This is the one task where batching is capped by memory.
  • Sentence similarity.
    • The pooling mode comes from sentence-transformers' modules.json and 1_Pooling/config.json (mean, CLS or max), and normalisation from 2_Normalize.
    • Similarity is cosine.
    • BertEmbedder stays as is for existing callers.
  • Cross-encoder reranking. Pair encoding, then the model's raw logit, with the activation that the model's sentence-transformers config names. The parity fixture pins the activation used for each model rather than assuming it.
  • Zero-shot (stretch). The NLI-template method of transformers' zero-shot pipeline, over any NLI classifier (DeBERTa-v3 NLI).

Long text:

  • Truncation is the default for classification and similarity, with a flag on the result: TokenEncoding already records truncated.
  • Striding: NER and QA split long input into overlapping windows (max_length, stride/doc_stride).
    • NER keeps, for each token, the prediction from the window where the token is furthest from an edge, then aggregates.
    • QA takes the best span over all windows.
    • This matches transformers when return_overflowing_tokens is on.

Runner interface. Each task calls an EncoderRunner:

interface EncoderRunner {
  method : virtual : public : Inputs() ~ String[];
  method : virtual : public : Run(inputs : Vector<API.Models.Tensor>, outputs : String[]) ~ Vector<API.Models.Tensor>;
}

OnnxRunner is the only implementation in Phase A. Phase B adds TorchRunner in its own library, so a model defined and fine-tuned in Objeck runs through the same TextClassifier (§8.1).

8.2 The native shim (libobjk_torch)

  • libtorch has no general C API, so Objeck gets a C++ shim. It is built per platform against that platform's libtorch, exactly as core/lib/onnx builds libobjk_onnx against ONNX Runtime.
  • The shim exposes the Objeck native-function convention:
    • tensors are opaque int64 handles in a handle table;
    • every function returns a status, with the libtorch exception message on failure.
  • Its surface, grown by phase, starting with what BERT needs:
    • creation: zeros, ones, randn, arange, from_blob, from_floats;
    • dtype and device moves;
    • shape and views;
    • pointwise and reduction math;
    • matmul/bmm;
    • softmax, log_softmax, gelu, tanh, relu;
    • layer_norm, embedding, dropout;
    • cross_entropy, binary_cross_entropy_with_logits;
    • scaled_dot_product_attention;
    • autograd: backward, grad, requires_grad, no_grad;
    • AdamW / SGD steps over a parameter list;
    • a seeded RNG;
    • live-handle counts.
  • ABI choice (decision D8).
    • Option 1, recommended: build against the regular C++ API, pinned to one libtorch version per Objeck release, and rebuild the shim on each upgrade, the way the ONNX binding pins its runtime.
    • Option 2: PyTorch's new Stable ABI (torch::stable, "binary-compatible … across PyTorch versions"). It would let users drop in a newer libtorch, CUDA builds included, without rebuilding. B0 checks whether its op set covers the surface above. Its documented purpose is operator extensions, so the default assumption is that it does not yet cover autograd and optimizers.
  • Windows: MSVC, /MD, matching libtorch's CRT.
  • Loading: the shim is loaded the way the ONNX library is loaded. B0 checks that torch_cpu.dll and onnxruntime.dll coexist in one Objeck process; both bring OpenMP or thread-pool runtimes.

8.3 Architectures in Objeck, weights from safetensors

System.AI.NN provides the following building blocks, each with Forward and named parameters in Hugging Face's naming:

  • Module, Parameter;
  • Linear, Embedding, LayerNorm, RMSNorm, Dropout;
  • MultiHeadAttention, with an optional causal mask and an optional KV cache;
  • Conv1d, Conv2d, GELU, Sequential.

Because the parameter names match, module->LoadState(SafeTensors->Read(path)) maps one-to-one onto a Hugging Face checkpoint.

BERT, as it is written in System.AI.Transformers (abridged):

class BertLayer from Module {
  @attention : MultiHeadAttention;    # attention.self.{query,key,value}, attention.output.dense
  @attn_norm : LayerNorm;             # attention.output.LayerNorm
  @intermediate : Linear;             # intermediate.dense
  @output : Linear;                   # output.dense
  @out_norm : LayerNorm;              # output.LayerNorm
  @dropout : Dropout;

  method : public : Forward(x : Tensor, mask : Tensor) ~ Tensor {
    a := @attn_norm->Forward(x->Add(@dropout->Forward(@attention->Forward(x, mask))));
    h := @intermediate->Forward(a)->Gelu();
    return @out_norm->Forward(a->Add(@dropout->Forward(@output->Forward(h))));
  }
}

class BertForSequenceClassification from Module {
  @bert : BertModel;                  # embeddings + encoder.layer.N + pooler
  @classifier : Linear;

  function : FromPretrained(dir : String) ~ BertForSequenceClassification {
    config := ModelConfig->Read(dir + "/config.json");            # hidden_size, num_attention_heads, id2label, …
    model := BertForSequenceClassification->New(config);
    model->LoadState(SafeTensors->Read(dir + "/model.safetensors"));   # strict: missing or unexpected names fail
    return model;
  }

  method : public : Forward(ids : Tensor, mask : Tensor, types : Tensor) ~ Tensor {
    return @classifier->Forward(@bert->Forward(ids, mask, types)->GetPooled());
  }
}

use System.AI.Transformers;
use System.AI.Optim;
use System.AI.Data;

model := DistilBertForSequenceClassification->FromPretrained(hub->Snapshot("distilbert/distilbert-base-cased"), 2);
model->To(Device->Best());                                    # CUDA / MPS / XPU when present, else CPU

tokenizer := TokenizerJson->Load(dir + "/tokenizer.json");
train := TextDataset->New(texts, labels, tokenizer, 128);     # pads to MAX_SEQ_LENGTH
loader := DataLoader->New(train, 16, true, Generator->New(42));   # batch, shuffle, seed

optimizer := AdamW->New(model->Parameters(), 2e-5, 0.01);     # lr, weight decay; no decay on bias / LayerNorm
schedule := LinearSchedule->New(optimizer, warmup, total);

trainer := Trainer->New(model, optimizer, schedule);
trainer->SetClassWeights([1.0, 99.0]);                        # weighted cross-entropy for the lab's POSRATIO runs
trainer->OnStep(\(StepInfo) ~ Nil : (s) => { s->GetLoss()->PrintLine(); });
trainer->Fit(loader, 3);                                      # epochs

model->Save("malware_distilbert");                            # config.json + model.safetensors + tokenizer.json
classifier := TextClassifier->New(TorchRunner->New(model), tokenizer);   # the Phase A API, the torch backend

FineTuner is a convenience over these calls, and implements ScoreModel.

9. ONNX as the export target (Phase E)

Every op an Objeck model runs goes through the tensor API, so the API can record a forward pass and write the ONNX graph:

  • OnnxExporter->Export(model, example_inputs, path);
  • dynamic batch and sequence axes;
  • each op in the shim's surface maps to one or a few standard ONNX ops;
  • the protobuf is written in Objeck;
  • the weights become initializers.

A model fine-tuned in Objeck can then run in API.Onnx, on any execution provider ONNX Runtime has, including the NPUs and GPUs libtorch does not reach (§3.3). That narrows the GPU gaps for inference.

The test: export, then run in Objeck's ONNX session, in Python ONNX Runtime and against the torch-backend logits, within 1e-5.

10. The lab, end to end

The user's Lab 1 Part 4 fine-tunes distilbert-base-cased as a binary malware classifier over API-call sequences on Colab: MAX_SEQ_LENGTH 128, AdamW, linear warm-up. part4_bert_malware.py evaluates in PyTorch and does not save the model (no save_pretrained call).

10.1 First target: run the Colab model from Objeck (Phase A1)

  1. In the notebook (the user's code, Python, once):
    • give the model real labels with model.config.id2label = {0: "benign", 1: "malware"};
    • save it with model.save_pretrained(out) and tokenizer.save_pretrained(out);
    • export it with optimum-cli export onnx --model out --task text-classification out/onnx.
  2. What the export will look like, going by the measured DistilBERT classifier signature (§7.2):
    • inputs input_ids and attention_mask, INT64 [batch, sequence];
    • output logits FP32 [batch, 2];
    • a cased WordPiece tokenizer (lowercase false).
  3. In Objeck:
classifier := TextClassifier->New("malware_distilbert");
preds := classifier->Classify(test_sequences);

Then compute precision, recall and F1 with System.ML's existing metrics.

  1. The check:
    • Objeck's malware probability matches Python's softmax for the lab's fixed test set within 1e-5 (ONNX against ONNX) and 1e-4 (against PyTorch);
    • the predicted classes are identical, so the metrics are identical.

10.2 Second target: fine-tune it in Objeck (Phase B2)

  • The same experiment runs with Trainer (§8.6): POSRATIO, unweighted and weighted, then MAX_SEQ_LENGTH, then learning rate.
  • On CPU it takes 33–39 minutes per run for DistilBERT at 5,000 rows (§8.5).
  • The check: the loss trajectory over the first 20 steps matches PyTorch within 1e-4 relative, with the same initial safetensors, batch order and seed, dropout off for the parity run, and one thread.
  • Then the final metrics are within run-to-run noise of the Python lab.

  • DirectML. Objeck's Windows ONNX GPU path depends on DirectML, which its README says is in maintenance mode (§3.3). It needs its own design for a maintained Windows execution provider.
