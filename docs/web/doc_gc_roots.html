GC roots: a precise root model for the interpreter and both JITs

← All docsdocs/GC_ROOTS_DESIGN.md on GitHub

Written 2026-10-29 against master c816f3f9ae, before any implementation. It was prompted by two suspected JIT root bugs (jit_stale_spill_slot, jit_inline_local_root) and a run of collector fixes that each patched one consequence of the same assumption. This was a design for review when it was written, and nothing below had landed. Phases 0 to 6 have since merged (#1511 was the last); the status blocks that follow are the record of what was built and how it differs, and the rest of the page is the design they implemented.

1. Summary

The collector does not know which words in a frame are references. It finds roots in three ways:

  • it walks the declared locals by their declared types;
  • it scans untyped words conservatively, marking anything that IsAllocated accepts;
  • it relocates anything whose target has been forwarded (FixupSlot).

The untyped words are:

  • the interpreter's operand stacks;
  • the and/or slot;
  • a fixed window of JIT_TMP_LOOK_BACK (16) words beside every JIT frame, whether or not the frame wrote them.

Neither JIT backend tells the collector which of those words hold a live reference at a safepoint.

That guess has three consequences. Each is demonstrated below on a fresh Windows x64 build of master:

  1. Dead objects stay reachable. A spill slot that is never cleared, or never zeroed at entry, keeps whatever it last held. jit_stale_spill_slot keeps a dead 32 MB array alive (§3.1).
  2. Integers are rewritten. The nursery moves objects, and fixup "relocates" any untyped word equal to a forwarded object's address. That includes an Int that holds an address, such as GetInstanceID(). In the reproducer, 242 of 2,000 such integers changed value across a minor collection, interpreted and compiled alike (§3.3). This is a correctness bug, not a leak.
  3. Every new slot kind became a separate fix. The and/or slot, pending registers at a loop poll, self's frame copy, frame layout and closure captures were each fixed one at a time (§4).

The proposal has three parts:

  • one shared bytecode analysis that says, for every instruction, which operand-stack depths and which untyped slots hold references;
  • interpreter frames read that analysis as a stack map;
  • JIT frames spill references only to reference-only slots that the collector scans by type, and clear them after reload.

Conservative scanning of frames and stacks is then removed, along with the window and the symptom patches that exist only because of it (§7, phase 5).

Verdicts on the two suspected bugs:

  • jit_stale_spill_slot is real, JIT-only, and has two paths. First, AMD64 entry zeroing skips TMP_REG_0 on both ABIs. Second, spill slots are never cleared, so a frame keeps what it spilled for as long as it runs. ARM64 has only the second path.
  • jit_inline_local_root is refuted. The AMD64 JIT inliner has been switched off since f871a89252 (2026-04-01): ProcessInlineMethod has no caller. ARM64 has no JIT inliner. The test never reached either. The dead inliner should be deleted (phase 5), because enabling it again would introduce exactly the defect the test describes.

2.1 --jit=off does not mean "interpreter only"

--jit=off (and OBJECK_JIT_DISABLE=1) only raises the auto-JIT threshold. A native method is still compiled. Under --jit=off, OBJECK_JIT_REPORT=1 prints [jit] Probe2:Leave:: compiled for a native method, and System.String:Get is compiled too, because library methods are native as well.

The usage text says "'off' runs the interpreter only". The earlier finding that jit_stale_spill_slot "fails with the JIT off" came from this: the test's methods are all native. With native removed:

jit_stale_spill_slot, no native--jit=off--jit=1default (10)

-opt s3PASSFAILPASS

Two consequences follow:

  • The nightly differential's s0/off configuration (#1443's table) is not interpreter-only either.
  • --jit=off needs its own fix, or its help text needs to change. That is reported separately and is not part of this design.

3. What the two tests actually show

3.1 Stale spill slots (real)

Path 1: entry zeroing misses TMP_REG_0 (AMD64, both ABIs).

JitAmd64::RegisterRoot zeroes ((offset - 8) >> 3) + 10 words upward from the lowest local. On Win64 the locals plus the RED_ZONE word take offset / 8 words, so the count stops one word short of TMP_REG_0 (RBP-32). POSIX misses TMP_REG_0 (RBP-88) the same way.

The - 8 dates from the six-slot layout (+ 6). 5555f2960b (2026-09-09) widened the slots to ten without changing it.

In the test, Leave() spills the 32 MB array to TMP_REG_0 across the StaleSmall constructor and returns. Churn() is then entered at the same frame pointer and never writes that slot, so every collection under Churn() finds the array there.

Changing the count to (offset >> 3) + 10 makes s0 pass. That one-line change is kept only as evidence, on the local branch scratch/amd64-tmp-reg0-entry-zeroing-evidence; it is not the fix. The main checkout's deploy build from 2026-10-22, which has the same count, passes the same test, so frame placement decides whether this path triggers. The 10-24 call-stack change (13daaacfb2) is the likely trigger; this was not bisected.

Path 2: spills are never cleared (AMD64 and ARM64).

At -opt s3, the compiler inlines Leave into Run as bytecode. MakeBig's result is pending in Run's own frame across StaleSmall:New, so ProcessStackCallback spills it to Run's TMP_REG_0, reloads it for Keep, and leaves the slot as it is. Run stays live while Garbage() runs.

A trace build that prints the window words the collector finds allocated shows the array in every collection:

[gc] jit frame 'JitStaleSpillSlot:Run:' mem=...EB60 dclrs=2
[gc]   window 10 @...EBC0 -> 0000027E5B6D0060 size=33554457

Window word 10 on Win64 is RBP-32, which is TMP_REG_0. ARM64 zeroes all six TMP_X slots at entry (RegisterRoot), so it has path 2 only.

Severity: the effect is retention, at most one object per stale slot per live frame. Nothing is freed while still in use. It becomes serious when the object is large, as with the 32 MB array here.

3.2 Inlined callee locals (refuted)

The claim is that the AMD64 JIT pastes small callees into the caller and puts their locals below the walked region. The layout part is true of the code: inline_local_offset starts below the caller's locals, and the collector walks only org_local_space. But that code never runs:

  • The JIT inliner never runs. ProcessInlineMethod has no caller. f871a89252 replaced the call with the callback path ("disable ProcessInlineMethod for MTHD_CALL"). CanInlineMethod is still called, but only to size extra_inline_space, which is dead frame space today.
  • At -opt s0, Fill is compiled as a separate method. Its s->Size() is a MTHD_CALL, so CanInlineMethod would refuse it anyway.
  • At -opt s3, the compiler inlines Fill as bytecode. Its locals become Run's declared locals, which the collector walks.
  • A rewritten test that the JIT inliner would accept still passes. It has no calls and no branches, at most 20 instructions, and returns s[0]. It passes at s0, s1 and s3 under --jit=off and --jit=1, because nothing inlines it.
  • ARM64 has no JIT inliner.

The latent hazard is real: re-enabling ProcessInlineMethod would reintroduce exactly this defect. Phase 5 deletes it. Any future JIT inliner must give inlined locals declared, walked slots.

3.3 Integers rewritten by fixup (new; interpreter and JIT)

FixupRoots runs FixupSlot over every operand-stack word and every window word. The comment there says it "validates the forwarding target so a plain integer that merely aliases the young address range is not misread". But the check cannot tell an integer from a reference: an integer equal to a young object's start address passes it.

GetInstanceID() returns exactly such an integer (LOAD_INST_UID compiles to LOAD_INST_MEM). The reproducer:

o := Box->New(i);
before := o->GetInstanceID();
# o->GetInstanceID() is pending (operand stack / spill slot) while Churn allocates
if(Same(o->GetInstanceID(), Churn(i), before) = false) { bad += 1; };

Run with --nursery=64k, 2,000 iterations, no native:

--jit=off--jit=1
-opt s0FAIL, 242 changedFAIL, 242
-opt s3FAIL, 242FAIL, 242

With the default 128 MB nursery it passes, because no minor collection lands in the window. The 2026-10-22 binary fails the same way, so this is not a regression of this cycle.

A related but separate problem: an instance ID is an address, so it changes when the object is promoted. That is an identity-stability bug, out of scope here.

5.2 Target rules

A word is a root if and only if the collector is told it is a reference at the safepoint where the collection happens. No word is ever relocated on a guess.

  1. Declared locals. Precise by declaration, as today. Both backends already lay frames out from declarations (4b67aa39ba), and entry zeroing makes a not-yet-written slot hold 0. Liveness is not required: a dead local that holds a reference is retention, not corruption, and the language makes it visible.
  2. The and/or slot. Typed per pc by the shared analysis (§6.1): a reference where the join merges references, an integer otherwise. It is no longer conservative.
  3. Self. frame->mem[0] is the only root. INSTANCE_MEM is a derived cache that is never scanned and is reloaded after every GC-reachable call. That rule exists today; the design states it as an invariant and the verifier checks it.
  4. Operand stacks. Typed per (method, pc) by the shared analysis. A depth is marked and relocated only if it is a reference. Integers are never touched, which fixes §3.3.
  5. Pending values in JIT code. A reference goes to a reference-only spill slot, which is typed, scanned precisely, zeroed at entry and cleared after reload. An integer or float goes to slots the collector never scans. This fixes §3.1 and §3.3 in compiled code.
  6. Scratch saves. These go to non-scanned slots. A scratch value is never a reference the collector needs: no collection can happen between a save and its restore inside one instruction.
  7. Saved frame words and float temps. Never scanned.
  8. Closure captures. Unchanged for roots. The capture block gets a type of its own in phase 6 (the heap side), which retires 193f076fdd's conservative dirty-block path.
  9. Native and trap C++ code. The convention stays: a reference held across an allocation lives on the operand stack. The analysis types an instruction's inputs as of the instruction's start, and a trap that pushes intermediate references must declare them. Phase 2 audits the traps; the verifier runs report-only until that audit is done.

5.3 Conservative scanning afterwards

There is none in frame or stack root discovery. The old scan survives in one place: the audit mode OBJECK_GC_ROOTS=audit, which runs the conservative scan beside the precise one and reports any allocated word the conservative scan would mark that the precise scan did not. That is the migration safety net. During phases 1-4 it reports, and it never changes what is marked.

6. How live references are reported

6.1 One shared analysis: RefMap (in jit_common)

The bytecode does not carry reference types on the stack. LOAD_INT_VAR loads objects and integers alike, and Int[] and object arrays share INT_TYPE. So the first piece is an abstract interpretation over a method's bytecode that tracks, for each operand-stack depth and the and/or slot, one of {int, ref, float, unknown}:

sourceresult
LOAD_INT_VARthe slot's declared kind
NEW_*ref
LOAD_INST_MEMref
MTHD_CALLthe callee's return type
arithmeticint
array element loadsthe array's declared element kind, where the declaration knows it
joinsthe meet of the incoming kinds

The analysis runs once per method on first need and is cached. It has three consumers: the interpreter (read lazily at collection time), AMD64 (at compile time) and ARM64 (at compile time).

unknown is the open question. Phase 1 measures how often it occurs across the regression suite and the library before anything depends on it. Any residue gets a compiler-emitted annotation instead of a guess.

6.2 Interpreter: stack maps per (method, pc)

The map is read only when a collection walks the frame, and indexed by the instruction in progress, StackFrame::cur_ip (see the status note at the top). Recording it is one store on the dispatch loop's default path, which only instructions that can collect take, and one at the safepoint poll.

B is the minimum patch. It is rejected as a root model because it keeps the conservative window and does not fix §3.3.

A is the most general, but a wrong map entry fails toward corruption, and it adds a table format to two hand-written backends.

C gets the same safety from a smaller change, and every bug it can have fails toward retention. Recommendation: C. A can come later if liveness inside long frames ever measures as a problem.

Under C, the collector walks each JIT frame as: the declared slots (typed), the and/or slot (typed by RefMap at the frame's current pc), then the TMP_REF_* slots (typed ref, 0 when empty). Nothing else. The and/or slot needs the pc, and this design has not yet confirmed that a JIT frame records it at every GC-reachable call. Phase 1 checks this. If it does not, phase 3 adds one store of the instruction index per such call, which is option A's cost for this one slot only.

What v2026.10.2 needs

Recommendation: none of phases 1-6. Ship 10.2 without them.

  • The spill-slot defect is retention: at most one object per slot per live frame, nothing freed while in use.
  • The integer rewrite needs an address-valued Int to be pending across a minor collection. It is in v2026.10.1 and the 10-22 build alike, so it is not a regression of this cycle.
  • Phases 3-4 change frame layout constants in both hand-written backends, and phase 4 can only be proven on CI's arm64 legs. That is the wrong risk to take the day before a tag.

If one item must go in, take phase 0's --jit=off fix. It is small and VM-only, and it makes the nightly differential's "interpreter" column mean what it says.

The one-line entry-zeroing change would also be safe, but it fixes one path of one symptom, which is the pattern this design replaces. It stays on the evidence branch unless the user decides otherwise.

gc_root_coverage generates, from a seed (printed on failure, reproducible with --seed), methods that:

  • keep a random mix of Int values (including GetInstanceID()), objects, arrays and closures pending on the stack;
  • put them in and/or joins, conditional constructor arguments and loop safepoints;
  • allocate between every pair of uses.

It checks every value afterwards: integers unchanged, objects with their fields intact. It runs under OBJECK_GC_VERIFY=checkmark with --nursery=64k, at s0 and s3, with --jit=off and with OBJECK_JIT_THRESHOLD=1, plus a two-thread variant that parks at loop polls. The fixed seeds run in the regression suite, and the nightly runs fresh seeds. During phase 1 OBJECK_GC_ROOTS=audit must report zero differences across the suite before phase 2 starts.

10. Not established

  • #1443 (query_url_cache_processes, Windows only, parent at s3/jit1, children get "no response from the server"). Neither mechanism here is shown to cause it:
    • retention cannot produce a wrong or missing response;
    • the integer rewrite is not JIT-only and not Windows-only.

One link to the harness is real: that differential's s0/off column is not interpreter-only (§2.1), so "passes with the JIT off" has meant less than it appeared. #1443 was not reproduced here.

  • ARM64 behaviour of jit_stale_spill_slot. Inferred from the code (path 2 only), not run. CI's arm64 legs will run it when the test lands.
  • When the s0 trigger appeared. It is absent on 10-22 and present on master, and it was not bisected.
  • Heap Int[] elements are rewritten by a minor collection (found 2026-10-31; fixed by phase 6, the Int[] tag, 2026-11-01). An Int[] and an object array share INT_TYPE on the heap (§6.1 says the same of the bytecode), so the collector's fixup of a reachable array's elements cannot tell an integer from a reference and relocates any element equal to a forwarded young object's address. Evidence, with the test hook from PR 1483 (Runtime->TestAddressOf, OBJECK_GC_TEST_HOOKS=1): a test that stores an object's address in an Int[] element and then allocates enough for a minor collection sees the element change in 242 of 2,000 iterations, in default mode (no OBJECK_GC_ROOTS), interpreted and compiled alike. This is the heap-side twin of §3.3: it is not a root problem, and the reference maps cannot reach it, because the array header is what lacks the type. It needs a distinct reference-array tag from the compiler, which is phase 6 territory (the heap side), and is not fixed in phases 1-5.
