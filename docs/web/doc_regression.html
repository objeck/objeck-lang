Objeck Language Regression Test Suite

All documentationView programs/regression/README.md on GitHub

This regression test suite validates the compiler, virtual machine, JIT and libraries after every change. It has 812 .obs files (the generated TESTS.md lists every one, by category, with what it checks; 128 files are named bad_*; 139 carry an EXPECT_COMPILE_ERROR (116) or EXPECT_RUNTIME_ERROR (23) marker). The map of every other assurance mechanism in the repository (fuzzers, verifiers, nightly jobs, static analysis) is docs/TESTING_AND_ASSURANCE.md. It covers:

Purpose

  • Core language - classes, generics, closures and lambdas, records, strings, collections, exceptions
  • JIT - AMD64 and ARM64 code generation (jit_*, arm64_*)
  • GC and concurrency - minor and major collection, write barriers, threads
  • Compiler and runtime errors - negative tests (bad_*) that must be rejected, with the expected message
  • Libraries - JSON, XML, regex, networking and TLS, ODBC, ML and AI, OpenGL, ONNX
  • Tools - debugger, DAP, LSP and MCP entry points

TESTS.md is generated by gen_manifest.py in this directory; it also lists the 14 debugger tests that run_debugger_tests.sh drives. Do not commit it in a pull request: the Regression test manifest workflow regenerates it on master after each merge that changes a test. When every pull request carried its own copy, each merge made every other open pull request conflict on it.

Running Tests

Build a deploy tree first (core/release/deploy_windows.cmd x64|arm64, core/release/deploy_posix.sh x64|arm64 or core/release/deploy_macos_arm64.sh). The runners use core/release/deploy-<arch> when it exists and core/release/deploy otherwise.

Linux/macOS

cd programs/regression
chmod +x run_regression.sh
./run_regression.sh x64          # or arm64

Windows

cd programs\regression
run_regression.cmd x64      REM For x64 build
run_regression.cmd arm64    REM For ARM64 build

Each test is compiled with obc -opt s3 -lib cipher,collect,xml,json (plus any libraries its # EXTRA_LIBS: line names) and run with obr. Compiler logs and program output go to results/. Apart from the negative tests (see the directives below), the runners judge a test by its exit code: 0 passes, anything else fails. A test that prints a line starting with SKIP: and exits 0 counts as skipped, not passed.

Environment variables both runners honor:

  • TEST_TIMEOUT - seconds allowed per test run (the POSIX runner defaults to 60, the Windows runner to 300, the value the nightly runs use)
  • OBJECK_VM_ARGS - extra obr options for every test, e.g. --gc-threshold=64k
  • OBJECK_GL_REQUIRED=1, OBJECK_REQUIRE_ODBC=1 - turn the OpenGL and ODBC tests' environment-dependent skips into failures (CI sets them on the legs that have a context and the objeck_sqlite_test data source)

Only the POSIX runner honors REGRESSION_SHARD=i/n, which runs every nth test starting at the ith (0-based) so the suite can run as n processes side by side (tools/cicd/local_linux.sh does).

How a result is decided. Compile, then one run of obr with the default JIT:

Test kindPasses when
ordinaryobr exits 0 and the output has no line starting SKIP: (such a test is counted as skipped)
# EXPECT_COMPILE_ERROR: <message>the compile fails, the log is non-empty and contains <message> (case-sensitive, trimmed); with # EXPECT_ERROR_COUNT: <n> the log must also hold exactly n error lines (lines naming a .obs position that are not warnings)
# EXPECT_RUNTIME_ERRORobr exits non-zero with some output; neither the exit code nor the text is checked
anya run longer than TEST_TIMEOUT fails, whatever the markers say

The suite compiles at -opt s3 only, with one fixed library list, and runs each test once, so it cannot by itself find a bug that needs the optimizer off, a particular threshold, a particular heap size or a particular interleaving. That is what the second CI pass (OBJECK_JIT_THRESHOLD=1) and the nightly runs below add.

OBJECK_JIT_THRESHOLD=1 makes obr compile every method on its first call; CI runs the suite a second time with it.

Other runners in this directory (run by ci-build.yml on every leg unless the last column says otherwise):

RunnerWhat it checksWhere it runs

None of the Python runners can find a bug outside the programs it feeds them: the robustness gates catch crashes, hangs and diagnostics that drift, not a wrong error message that happens to land near the mutation, and the differential runner finds divergence between configurations, not an error every configuration shares.

Test Organization

The file-name prefix decides a test's category in TESTS.md (core_, jit_, arm64_, bad_, collect_, ml_ and so on; the mapping is CATS in gen_manifest.py, and a name that matches none is filed under Other). Directives are comment lines starting at column 0:

DirectiveEffect
# EXTRA_LIBS: net,gen_collectLinks these libraries as well (comma-separated, no spaces)
# EXPECT_COMPILE_ERROR: <message>Passes only if compilation fails and the compiler output contains <message>
# EXPECT_RUNTIME_ERRORPasses only if obr exits non-zero with output
# JIT_DISABLERuns the test with the JIT off; the next line must be # reason: ... (tools/cicd/check_jit_optouts.py)
# EXPECT_ERROR_COUNT: <n>With # EXPECT_COMPILE_ERROR, the compiler log must hold exactly n error lines
# VERIFY_SKIP, # GC_STRESS_SKIPSkipped in the nightly heap-verifier and forced-GC-threshold runs; the next line must be # reason: ... naming the run that failed (none carries VERIFY_SKIP today, two carry GC_STRESS_SKIP)
# DIFF_CONFIGS, # DIFF_REQUIRES_JIT, # NONDETERMINISTIC_OUTPUT, # DIFF_SERIAL, # DIFF_TIMEOUT: <s>Read by run_differential.py only; each marker that removes coverage needs a # reason: line (tools/cicd/check_diff_markers.py)

Data a test reads lives under data/, found relative to this directory (every runner runs tests from here). data/bert/ holds three tiny BERT-shaped ONNX models, their vocabulary and gen_tiny_bert.py, which regenerates them byte-for-byte; docs/ML_BERT_DESIGN.md describes them.

Adding New Tests

  1. Create a new .obs file in this directory
  2. Name it descriptively: category_feature.obs
  3. Include a comment header explaining what it tests; gen_manifest.py takes the test's TESTS.md description from it
  4. Output PASS or FAIL messages for automation
  5. Exit with code 0 on success, non-zero on failure (Runtime->Exit(1)). Printing FAIL is not enough: a test that returns normally exits 0 and is scored a pass, and CI's tools/cicd/check_test_exit_codes.py rejects a test that prints FAIL with no exit path
  6. Leave TESTS.md alone: it is regenerated on master after the merge (run python gen_manifest.py locally to preview, but do not commit the result)

Test Template

#~
# Test Name
# Brief description of what this tests
# Related commit: <commit-hash>
~#

class MyTest {
    function : Main(args : String[]) ~ Nil {
        "Testing my feature..."->PrintLine();

        pass := true;

        # Your test logic here
        if(test_condition) {
            # Test passed
        } else {
            pass := false;
            "  FAIL: Description of failure"->PrintLine();
        };

        if(pass) {
            "PASS: My feature"->PrintLine();
        } else {
            "FAIL: My feature"->PrintLine();
            Runtime->Exit(1);
        };
    }
}

CI/CD Integration

This test suite runs automatically in GitHub Actions on:

  • Push to master
  • Pull requests to master

It runs natively on all five platforms (Windows x64 and ARM64, Linux x64 and ARM64, macOS ARM64), twice on each: once as is and once with OBJECK_JIT_THRESHOLD=1. The same job runs the debugger, DAP, VM-flag and compiler-robustness runners from this directory, and CI's tools job lints the tests themselves (check_test_exit_codes.py, check_jit_optouts.py, check_diff_markers.py in tools/cicd). .github/workflows/nightly-hardening.yml runs daily at 07:23 UTC and on dispatch, against the binaries of the latest green master CI run: run_differential.py, the program fuzzer (tools/fuzz/run_fuzz.py), this suite twice under the heap verifier (OBJECK_NURSERY=256k OBJECK_GC_VERIFY=1, then OBJECK_VM_ARGS=--gc-threshold=64k OBJECK_GC_VERIFY=1), loops of minor_gc_stress, core_thread_gc_stress and jit_gc_stress in both JIT modes, and a libFuzzer run on the .obe loader.

See .github/workflows/ci-build.yml for CI configuration.
