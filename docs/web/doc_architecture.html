1. Complete System Overview

The whole toolchain, from the editor to the five platforms a release ships to. Source is compiled by obc into an executable (.obe) or a library (.obl); obr runs it, interpreting until a method is hot and then compiling it to native code. The language server analyzes the same source with the compiler's own front end, linked into a native library.

Key components:

  • Compiler (obc): scanner, parser and context analyzer, an intermediate emitter, an optimizer with four levels (s0–s3, s3 by default), and a linker that reads .obl libraries. Libraries record their methods' parameter names and type parameters, so named arguments and generic inference work across binaries.
  • VM (obr): a stack interpreter that JIT-compiles hot methods for AMD64 and ARM64. Errors under ?-> or try recover in either mode; a compiled method reports a status the interpreter that owns the handler acts on.
  • Memory: generational, multithreaded garbage collection; C++ code that stores into an old object takes a write barrier.
  • Language server: written in Objeck (tools/lsp), analyzing with the compiler's own front end through libobjk_diags, so editor diagnostics match obc.
  • Tools: obi (REPL and full-screen editor), obd (debugger, also a Debug Adapter Protocol server), obu (updater that verifies signed manifests), obb (builds a native launcher for a program).
  • Libraries: 56 library sources; native modules wrap mbedTLS, nghttp2/ngtcp2, ODBC, ONNX Runtime, OpenCV, SDL2 and LAME.
  • CI and release: five platform legs on every pull request, the regression suite in three JIT modes, LSP, DAP and debugger tests, and a release gate that verifies all five platforms at one commit before tagging.

Key Features:

  • Tiered Execution: Interpreter → call counting → JIT
  • Hot Code Detection: Automatic at 10 calls (default; configurable via --jit=<calls> or OBJECK_JIT_THRESHOLD). A method with a loop is compiled on its first call instead, which is how Main gets compiled, and a thread's Run with a loop on entry; see docs/JIT_ENTRY_COMPILE_DESIGN.md
  • Platform-Specific JIT: Separate compilers for ARM64/x64
  • Efficient Memory: O(1) object lookups, generational GC

Call Depth

Each VM thread has its own call stack: an array of frame pointers, with the operand stack beside it (core/vm/call_stack.h). Calls may nest 16,384 frames deep by default; obr --call-depth=<frames> (or OBJECK_CALL_DEPTH) sets it, from 256 to 1,048,576. Until 2026-10 the limit was a fixed 256 frames, which the Rosetta "Man or boy" test (647 frames at k=10) and a recursive-descent parser on input nested a few hundred deep both exceeded.

  • Reserved, then committed as it deepens. A thread reserves address space for the maximum -- 8 bytes a frame, and 8 operand-stack words a frame -- and commits it as the stack grows, so an idle thread holds a page of frame array and 32 KB of operand stack, not the maximum. Measured on Windows x64 with 1,000 threads: the working set per thread is unchanged (94 KB idle). Frames themselves come from a per-thread pool, as before.
  • The operand stack is checked. An interpreted frame can leave values on it across a call (Sum(n - 1) + n keeps n), one word a frame for plain recursion. Nothing checked it when it was 768 words; each interpreted call now checks that 1,024 words are left.
  • The native stack is checked. A compiled frame is on the machine stack (about 520 bytes for a small method on x64), and so is each interpreter a JIT bridge starts. The compiled call site compares the stack pointer with the thread's floor -- its stack's lowest address plus 1 MB -- as well as the depth with the committed limit; the bridge and the interpreter's call into compiled code test the floor too. So running out of native stack is the same call stack bounds have been exceeded error, and recovers the same way. On Windows a thread the VM starts reserves 16 MB of native stack (1 KB a frame plus 2 MB for a larger --call-depth), and obr.exe and obi.exe reserve 32 MB for the main thread, so compiled code reaches the maximum. On Linux and macOS a thread gets 8 MB (macOS's default was 512 KB), more only for a --call-depth above the default, and the main thread has what ulimit -s gives it, typically 8 MB: about 12,000 small compiled frames, so there a compiled recursion stops before the maximum -- with the same error. Bigger POSIX stacks are not free: where transparent huge pages are on for every mapping, 2 MB pages back thread stacks, and 100 idle threads measured 48 MB resident with 8 MB stacks and 86 MB with 18 MB ones.
  • Full is a recoverable error. At the maximum, the error is a RuntimeError that try/on and ?-> recover from, compiled or interpreted (core_call_depth_max.obs). Unhandled, the listing shows the innermost 40 and outermost 10 frames and counts the rest.
  • Runtime->GetProperty("runtime.call.depth_max") reports the maximum.

Calls between compiled methods. Since v2026.9.1 a compiled caller enters a compiled callee's native entry directly — arguments in the caller's outgoing area, the frame record built in the callee's own frame, the result in XMM0 (D0 on ARM64) — with an inline cache at virtual and func-ref sites. The C++ callback bridge remains the slow path (a callee not yet compiled, a full call stack, a Nil receiver, a megamorphic site) and the only path for allocation, traps and conversions. A bound call costs 5.5 ns rather than 26.5 ns as a result. The call path is drawn in core/vm/arch/jit/README.md; the design and its measurements are in docs/JIT_CALLING_CONVENTION_DESIGN.md.

Face Recognition Example

use API.OpenCV, API.Onnx;

class FaceDemo {
  function : Main(args : String[]) ~ Nil {
    session := FaceSession->New("det_10g.onnx", "w600k_r50.onnx");

    img1 := Image->Load("person_a.jpg")->Convert(Image->Format->JPEG);
    img2 := Image->Load("person_b.jpg")->Convert(Image->Format->JPEG);

    r1 := session->Recognize(img1, 0.5);
    r2 := session->Recognize(img2, 0.5);

    faces1 := r1->GetResults();
    faces2 := r2->GetResults();
    sim := FaceSession->Compare(faces1[0]->GetEmbedding(), faces2[0]->GetEmbedding());
    "Similarity: {$sim}"->PrintLine();   # >0.35 = same person
    session->Close();
  }
}

Uses SCRFD 10G-KPS detector + ArcFace R50 recognizer from InsightFace buffalo_l. Runs on DirectML (Windows), CPU/CUDA (Linux), CoreML (macOS).

The 10 GB ceiling is the constraint that matters. 8. Memory Management

Multithreaded Collection (Cooperative Stop-the-World)

With multiple threads running, a collection cannot begin until every other thread has reached a known-safe point. Objeck uses a cooperative stop-the-world scheme rather than OS thread suspension:

  • Safepoints. The interpreter polls a safepoint every 1,024 instructions of its dispatch loop, and every allocation polls too. When a collection is requested, threads observe the request at their next safepoint and park until it completes. The AMD64 and ARM64 JITs emit the same poll at every loop header, so JIT-compiled code parks just as promptly; a compiled loop that starts with values still pending in registers spills them to the frame's scratch slots before it parks and reloads them after, because a register cannot be relocated.
  • Blocking calls. A thread about to block in a syscall (thread Join/sleep, socket I/O) brackets the call with begin/end-blocking markers so it counts as already parked — a collection never waits on a thread stuck in a blocking read.
  • Root scanning. Once all threads are parked, the collector marks from every thread's roots: static fields, each thread's full call stack including the currently-executing top-level frame, and each thread's operand stack. The set of roots scanned by the mark phase is exactly the set the fixup phase rewrites, so a live object can never be reclaimed while a reference to it survives in a parked thread's frame or operand stack.
  • Typed and untyped roots. A frame's declared locals are walked by type, so only object slots are followed. Some frame words have no declaration and are scanned conservatively: a word is treated as a reference only if it is the address of a live object, and relocated only through a genuine forwarding address. These are the operand stacks, the JIT's scratch slots, and a method's and/or slot, where a conditional (c ? a : b) leaves its value between the branch that stores it and the load after the join. A collection can fall in that gap, so the slot is a root in interpreted and compiled frames alike; before v2026.10.2 it was walked over, and a promoted object could be read back through its old nursery address.

The collector remains generational and non-OS-suspending; correctness comes from complete root coverage at the safepoint, not from freezing threads mid-instruction.

Old-Generation Membership

The collector must answer "is this address a live old-generation object?" for words taken from conservative scans — operand stacks and JIT temporaries — which may not be pointers at all. That rules out reading a flag from the candidate: the answer has to be decidable without dereferencing it. An object's header does carry GC_OLD_BIT, but reading it means trusting the address first.

So the old generation keeps a set of known-good addresses, PtrSet (core/vm/arch/ptr_set.h). It is open-addressed: keys live directly in one power-of-two array, probed linearly, with nullptr for an empty slot and an all-ones sentinel for a tombstone.

Two properties are deliberate and easy to undo by accident:

  • The hash is unmixed. Allocator addresses arrive in rising runs, so an unmixed hash keeps objects allocated near each other in slots near each other and a probe reuses the cache line the last one pulled in. Fibonacci mixing scatters them and costs a miss per lookup: over 2M realistic addresses, insert 6.8 ns and lookup 4.0 ns unmixed against 9.4 ns and 8.2 ns mixed.
  • There is no reference counting. Collection is generational mark-and-sweep. The header carries GC_MARK_BIT, GC_OLD_BIT, GC_RSET_BIT and GC_TRACED_BIT, and nothing counts references.

This replaced a std::unordered_set in v2026.9.7. That container is node-based, so every insert was a separate heap allocation, and the old generation gains one entry per promoted object — a minor collection paid that allocation once per survivor, on top of the object's own. On Windows it cost 239.5 ns per insert against the allocation's 38.5 ns. Promotion cost tracks promoted bytes rather than collection count, so it dominated: binarytrees(17) went from 2.392 s to 1.789 s (−25.2%) with peak RSS 194.6 MB → 179.1 MB, closing a 3.5× gap against Linux on the same hardware. ptr_set_test.cpp pins the behaviour the collector relies on, including that count() never dereferences its argument.

When Collections Run

  • Minor collections run when the nursery fills.
  • Major collections run when the old generation outgrows its threshold. After each major the next threshold is twice the live heap, never below 8 MB, so collection work stays proportional to allocation (before v2026.10.2 it grew only after eight majors in a row freed nothing, and a program holding a large table collected on nearly every array allocation).
  • --gc-threshold sets the threshold. It holds as given while a major leaves at least a quarter of it free, which is what lets a stress run such as the nightly --gc-threshold=64k collect every 64 KB; once more than three quarters of it survive, it scales with the live heap like the default, and returns to the given value once the live heap fits under it again.
  • Freed old-generation blocks go to one free list per size class, four classes per power of two from 16 bytes to 4 MB, so a reuse is a single pop rather than a search.

Key Characteristics:

  • O(1) Membership: the old generation is an open-addressed address set; no linear scans
  • Generational: a nursery that moves survivors (promote-and-forward with pointer fixup); an old generation swept in place
  • Write barrier: a store of a young object into an old one is recorded on a lock-free dirty list, so a minor GC need not scan the whole old generation; C++ code that stores into an old object must call WriteBarrier
  • Stop-the-World: cooperative, at safepoints (above)

HTTP Protocol Stack

Three protocols, and they do not share a serialization path — which is the single most important thing to know before touching this code.

ProtocolWhere the request is builtEngine
HTTP/1.1, HTTPSObjeck (net.obs, net_secure.obs) — assembled as textsockets + mbedTLS/OpenSSL
HTTP/2Native (common.cpp)nghttp2, all platforms
HTTP/3Native (common.cpp)ngtcp2 + nghttp3 + AWS-LC on POSIX, linked statically (tools/deps/build_quic_deps.sh); WinHTTP over MsQuic on Windows 11 / Server 2022+

Consequences that have each produced a real bug:

  • Request headers. HTTP/1.1 serializes headers in Objeck, so AddHeader worked there from the start. HTTP/2 and HTTP/3 hand off to a trap, and for a long time that trap had no headers argument — so AddHeader stored values that were silently dropped. They now travel as a String[] of alternating key/value through HTTP2_REQUEST_HDRS / HTTP3_REQUEST_HDRS.
  • Header validation lives in Objeck (Web.HTTP.HeaderCheck), not in the trap, precisely because HTTP/1.1 never reaches native code. A trap-side check could not have covered the line-oriented protocol where injection is worst. The native validators are defence in depth for the two protocols that do cross into C++.
  • HTTP/3 on Windows must assert the negotiated protocol. WinHTTP treats HTTP/3 as a preference and falls back to HTTP/2 or HTTP/1.1 transparently, so a 200 proves nothing. Every request checks WINHTTP_OPTION_HTTP_PROTOCOL_USED and fails unless HTTP/3 was really used. (Also non-obvious: WINHTTP_OPTION_ENABLE_HTTP_PROTOCOL must be set on the session handle before the request is created; setting it later is accepted and silently ignored.)
  • Capability is reportable. The traps compile unconditionally, so the presence of Http3Client proves nothing about whether an engine is behind it. Runtime->GetProperty("runtime.feature.http3") (and .http2) returns "1" only when one is compiled in — which is how a caller, or a test, tells unsupported apart from the network failed. The msys2 Windows builds have no HTTP/3 engine and correctly report "0".

10. Runtime Errors

Errors are objects. System.Error and its subclasses are raised with Runtime->Raise and caught by type with try { } on(e : T) { } finally { }; the runtime's own faults are raised the same way, as NilError, IndexError, DivideByZeroError, CastError and RuntimeError. ?-> still recovers from any error in a call chain, yielding Nil. An error nothing handles ends the program.

try {
  port := ParsePort(text, line);   # may Runtime->Raise(ConfigError->New(...))
}
on(e : ConfigError) {               # clauses are tested in order
  "line {$(e->GetLine())}: {$(e->GetMessage())}"->PrintLine();
}
on(e : Error) {                     # a catch-all goes last
  e->GetMessage()->PrintLine();
}
finally {                           # runs on every way out, return/break/continue included
  "checked"->PrintLine();
};

flowchart TB
    A["Error raised<br/>Runtime->Raise, or a runtime fault:<br/>Nil, index, divide by zero, cast"] --> B{"Handler on this<br/>thread's handler stack?"}
    B -->|yes| C["TryErrorRecovery: pop frames back to<br/>the handler's, restore the operand stack"]
    C --> D{"Which construct?"}
    D -->|"?-> / Try()"| E["The guarded chain yields Nil<br/>(?? may supply a default)"]
    D -->|"try / on"| F["First clause whose type matches runs;<br/>no match: the error goes on after finally"]
    F --> H["finally runs"]
    B -->|no| G["Message on stderr, the call stack,<br/>exit with status 1 (obd halts instead)"]

    style E fill:#e1ffe1
    style H fill:#e1ffe1
    style G fill:#ffe1e1
  • try/on/finally (EmitTry, design in docs/ERROR_HANDLING_DESIGN.md). The words are contextual, so no existing name stops compiling. The body runs in a TRY_START/TRY_END region; its handler fetches the error with GetLastError and tests each clause's type in order. The clauses run in a region of their own, so finally runs before an error raised in a clause goes on. An error no clause names is raised again after finally, so a typed try never swallows what it did not ask for. A return, break or continue that leaves the try closes its region and runs finally on the way out.
  • Fatal unless handled. The interpreter prints one >>> ... <<< line, such as >>> Attempting to dereference a 'Nil' memory instance <<<, >>> Index out of bounds: <index>,<size> <<< or >>> Divide by zero <<<, then lists the methods on the call stack (StackErrorUnwind) and exits with status 1. An invalid cast (>>> Invalid object cast ... <<<) and a full call stack are recovered like the rest when they happen in interpreted code. An invalid cast is now recovered inside a JIT-compiled method too (#925): the handler stack is per-thread, so the bridge callback that raises the cast can see it, and the callback reports a status (-5) that compiled code tests and carries out through its epilogue, where the interpreter already recovers a guard stub's status. The diagnostic is printed only when no handler is active, so a recovered cast is as silent as it is in interpreted code. A full call stack is recovered in compiled code too (since 2026-10): compiled frames consume the real C stack, which used to run out first and end the process in the OS. The compiled call site now tests the native stack as well as the depth (two compares a call; see Call Depth in section 3), so the call that would overrun it fails as a full call stack does, with no compiled frame left mid-way.
  • Try() and ?->. a?->b() is a->Try()->b(). The compiler brackets the rest of the chain with TRY_START and TRY_END (EmitTryIntrinsic); TRY_START pushes a handler, with the operand-stack position and call-stack depth to return to, on the thread's handler stack (which grows as needed). On a Nil dereference, a bad index or a zero divisor, TryErrorRecovery pops frames back to that depth, restores the operand stack and resumes at the handler, which stores Nil as the chain's value, and Runtime->GetLastError() says what it was. A compiled callee that returns one of those errors as its status is recovered the same way.
  • Otherwise() and ??. a ?? b is a->Otherwise(b): a Nil test, not a handler, so b is evaluated only when a is Nil.
  • The JIT leaves try regions alone. TRY_START and TRY_END are in neither backend's whitelist, so a method that holds a ?-> or a try stays interpreted: recovery needs the interpreter's handler stack. Errors raised inside a compiled callee still reach it.
  • Under the debugger (obd, built with _NO_HALT) an unguarded error halts the program instead of exiting, and DAP "uncaught" exception breakpoints stop there first (Debugger::OnRuntimeError).
  • Faults in the VM itself, a C++ exception such as std::bad_alloc, are caught at the top of Execute, or by the JIT bridge under compiled code, and reported as >>> virtual machine: ... <<<.

✅ Multi-tiered Execution: Interpreter → call counting → JIT compilation ✅ Platform-Specific JIT: Optimized ARM64 and x64 code generation ✅ Efficient Memory Management: O(1) lookups, generational GC ✅ Structured Errors: try/on/finally over typed Error objects, plus ?-> recovery ✅ Rich Library Ecosystem: 46 libraries including AI/ML, web servers ✅ Modern Development Tools: REPL, debugger, LSP support ✅ Automated CI/CD: Multi-platform testing with caching ✅ Cross-Platform: Linux x64/ARM64, macOS ARM64 (Apple silicon), Windows x64/ARM64 ✅ Full Unicode: Emoji and supplementary plane characters on all platforms including Windows console
