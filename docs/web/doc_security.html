The Objeck VM trust model

All documentationView docs/SECURITY_MODEL.md on GitHub

Short version: running an .obe is equivalent to running native code with the privileges of the obr process. The VM checks that a program file is well formed enough to load; it does not check that the bytecode inside is safe to execute. Do not run an .obe you would not run as a native executable, and do not treat obr as a sandbox. Isolation, where it is needed, comes from the operating system around the VM -- as the playground does with Docker.

This page says what the loader and interpreter check today, what they do not, what the web playground relies on, and what is planned. Every statement about the code cites the file and line it was read from (master, 2026-10-31); line numbers drift, so the function names are given as well.

Reporting a vulnerability is covered in SECURITY.md.

Who can do what

There are two ways for a program to do something dangerous, and the VM stops neither.

  1. By asking. A correct program compiled from ordinary source can read and write any file the process can, open sockets, run shell commands (TrapProcessor::SysCmd passes its argument to _wsystem/system, core/vm/common.cpp:4195-4213), and load native code: DllProxy->New(name) appends name to the native library directory with no check for path separators and loads the result (StackInterpreter::SharedLibraryLoad, core/vm/interpreter.cpp:3080-3132 for LoadLibraryW, :3198 for dlopen), so a name with ../ in it loads any file the process can read that carries the platform's library suffix, which the VM appends. A native library runs in-process with no restriction at all (see native_interface.md).
  2. By lying. An .obe that was not produced by obc -- or was edited after -- can contain instructions the compiler never emits. The interpreter trusts instruction operands, so such a file can read and write memory outside the VM's own structures. That makes a crafted .obe equivalent to native code even with every library withheld.

The first is the language working as designed. The second is the gap a bytecode verifier closes; the loader's verification pass closes part of it (below).

What the verification pass checks

Once a program has loaded and before any of it runs, Loader::Verify (core/vm/loader.cpp) relates each operand to the program it is part of. A program that breaks a rule is refused with >>> Invalid bytecode: <method>, instruction <n>: <rule> <<< and status 1. Every rule holds for every program the toolchain compiles: the 849 compiled regression programs (each links the standard libraries; a quarter are compiled again with -debug) all pass.

run_vm_flag_tests.py sections 30 and 34 change one operand of a freshly compiled program for each rule and require the refusal (section 34 with the default JIT, --jit=off and --jit=1). The stack rules were also run over 684 regression programs and 613 example, deploy and test programs, each compiled with every library: none is refused. The builder is run in a lenient mode here (a method it cannot model, or an instruction it has no rule for, is not a verdict); only a failure that makes the method unsafe refuses the program.

What it costs. One builder and one map serve every method of a program, the entry stacks live in one arena and a step works in a buffer it reuses, so the pass allocates per program rather than per method and instruction. Loading the largest image of the corpus (1.6 MB unpacked) under OBJECK_VERIFY_ONLY=1, the whole process, medians of 41: 51 ms before the trap and function-value rules and 36 ms with them on Linux x64; 78 and 47 ms on Windows x64. Counted with callgrind on Linux, loading that image took 298 million instructions before and 189 million with them, and running hello 37.2 and 25.2 million. The class rules, switched on later, cost load time only and nothing once a program runs: on the tree of 2026-11-27 (Linux x64) hello from start to finish takes 24.34 million instructions without them and 24.56 with (under 1% more; 4.18 and 4.29 ms, 2.6% more), and loading the largest image 192.6 and 194.1 million (30.2 and 31.0 ms). The rules' own work is 2.3 to 2.9% of a load's instructions; the same change won about 2% back from the parsing of signatures. The JIT builds its own map (other contents: the kinds of the stack words, no facts) only for a method it compiles, when it compiles it.

The interpreter also checks, when an array is indexed with more than one index, that the array has that many dimensions (ArrayIndex, core/vm/interpreter.cpp). A virtual call that finds no method in the receiver's classes, or finds one with no body or with other parameter or return words than its declaration, stops with >>> Invalid virtual call: ... <<< (StackInterpreter::ResolveVirtualTarget, checked when a class's override is first looked up, not on each call). The collector treats a function value whose id names no class as having no captures, and clearing a Nil array is the Nil runtime error it should always have been. So is a library method whose body is a trap when it is called on Nil (NilInstanceError, core/vm/common.cpp; SharedLibraryNilInstance, core/vm/interpreter.cpp). Such a method is not virtual, so the call never looked at the receiver and 30 handlers read through it: select on a Nil String, Serializer->Write, Deserializer->Read*, Timer->Start, FileReader->ReadByte, TCPSecureSocket->Close and DllProxy->Unload ended the VM with a segmentation fault from valid source. programs/regression/check_nil_trap_probe.py calls every public trap-bodied method of lang.obs on a Nil receiver, and with each reference argument Nil.

OBJECK_VERIFY_ONLY=1 makes obr load and verify a program and exit 0 without running it, or refuse it as above: for checking a file, and what the tests and the fuzz tools use to measure refusals without a program's side effects.

How this is measured

tools/fuzz/adhoc/obe_campaign.py changes compiled programs one opcode, operand, literal, instruction or record field at a time (and, for three in ten, at the byte level as obe_mutfuzz.py does) and runs each result with the default JIT, --jit=off and OBJECK_JIT_THRESHOLD=1. On 30,000 changes of 285 compiled regression programs, 582 crashed the VM before the rules from "a number is not read through" down were added (75 distinct faulting sites) and 45 with them; on 100,000 changes, 145 did (43 sites). The trap table and the function-value rules were then measured on one set of 30,000 changes of 278 programs: 45 crashed before them and 11 with them (5 sites).

The current figure is from a later run on more programs, so its changed programs are other ones and it does not continue that series: of 30,000 changes of 344 programs, 19 crash the VM (9 faulting sites), 18 once a trap-bodied method checks its receiver, and 15 with the class rules on as well, which is the VM as shipped. What the remaining ones are, and why the loader cannot refuse them yet, is in design/OBE_TYPE_VERIFIER.md.

No valid program is refused: every .obs in the repository that compiles on its own, at -opt s0 to s3 and a quarter again with -debug, and one program per library that names every documented class (769 of 779 classes link whole), 5,067 images, load under OBJECK_VERIFY_ONLY=1 (tools/fuzz/adhoc/obe_corpus_gate.py). With the class rules on the same gate was run again on the tree of 2026-11-27: 8,175 images on Linux x64 (773 of 783 documented classes link whole) and 8,175 on Windows x64, none refused, and the regression suite in every JIT mode. Programs that did not at first were each a compiler defect a rule exposed (CHANGELOG, v2026.11.4: a call with arguments on the result of ??; a return with no value after a try), or a rule that was wrong and was dropped: the class rules in particular are weaker than first written because of what the compiler does in valid programs (the design page says what).

What is still not checked

  • A reference's class. A local, a field, a capture and an array element are declared "object", not which class. A field read through an object of another class, a method called on one, or two object arguments exchanged is not caught unless the object is the method's own instance or one NEW_OBJ_INST just made. An instance variable is otherwise bounded by the largest object of any class, and an object-typed field may be given a number (an enum is one) and read through by another method. The classes an image does spell (the method's own instance, a parameter's or a result's qualified name, a cast, a new object) are checked, and only against an unrelated class; what is open is the class of a capture, a field, a local that is not a parameter, a generic's result and a parameter typed as an interface.
  • The kind of an array. A Byte[] read with an Int[]'s instruction reads past its end. The rule that tells Byte, Char, Float and word arrays apart is written and switched off (ARRAY_KIND_RULES): it refuses no valid program and, measured, none of the changed programs that crash.
  • Function values out of a field, a capture or an array element. Those carry no function type in an image, so a call through one is not related to the method it names.
  • What a trap does with a well-typed argument. The table types the words; a handler that trusts a length or an index it is given is the handler's bug, not a loader rule. The four traps no library method holds as written (FILE_TEMP_NAME's unused word, SOCK_UDP_BIND, and the two *_SRV_CERT traps nothing calls) are typed by count only.
  • Values nothing types. An array element, a field of another object and an untyped trap's result may be read through unchecked.
  • Instructions no path reaches. The verifier walks the paths of a method; the JIT compiles its instructions in order, the unreachable ones too, and one that pops an empty stack stops the compile with a null dereference.
  • The dimensions of an array in compiled code. The interpreter checks that an array indexed with several indices has that many dimensions; the compiled array access does not, and an Int[] can be returned where a String[,] is spelled (Int and object arrays are one kind to the verifier).
  • The bundled-executable path (buffer_end = nullptr) is verified but not bounds-checked while it is read.

So the rule at the top of this page still stands: a crafted .obe can still corrupt memory through the stack or through a trap's arguments.

The playground

playground.objeck.org runs untrusted programs. It does not rely on the VM for isolation. Its backend (programs/web-playground/backend) compiles the visitor's source with obc -- it never accepts an .obe -- and then runs it in a Docker container (app/services/sandbox.py:206-236):

  • network_mode="none" (sandbox.py:211)
  • a read-only root file system, and a 10 MB /tmp tmpfs mounted nosuid,nodev,noexec (sandbox.py:212, :215; size in app/config.py:22)
  • 128 MB of memory with no swap, half a CPU, and at most 32 processes (sandbox.py:216-220; values in app/config.py:19-21)
  • every capability dropped and no-new-privileges (sandbox.py:227-228)
  • a non-root sandbox user (sandbox.py:235)
  • timeout on both the compile and the run (container_command, sandbox.py:150-178)

Before that it refuses source that names bundles or calls the sandbox would not honour anyway -- System.API, System.IO.Filesystem, System.IO.Net (app/services/libmap.py:61-65), DllProxy, process and socket classes (app/services/validator.py:86-101) -- so a visitor gets a reason rather than a failure. That check is a lexical scan, by its own description "deliberately not a parser" (app/services/source_scan.py:13); it improves the error messages and is not the security boundary. The container is.

Anyone hosting Objeck for untrusted users should do the same: treat the VM process as hostile and contain it from outside.

Planned

  • Declared classes, completing the verifier: the static class of each object local, field, capture and array element, and the type of each function-typed one, written by the compiler and read by the loader. It is a format change, and three things the compiler does today have to change with it (a cast it checks and does not write, an enum declared as an object, a temporary declared as another type than it holds); the design is design/OBE_TYPE_VERIFIER.md. With it, "a crafted .obe is native code" becomes "a crafted .obe is refused".
  • Deny flags on obr, for capabilities a program should not have even when it asks: native libraries (DllProxy), running commands, the file system, the network. Each would make the matching traps fail as a runtime error. Together with a complete verifier, they would let obr itself enforce what the playground currently enforces only with a container and a source scan.

Until both exist, the rule at the top of this page stands.
